## Confirmed finding: unchecked persisted proposal map mints typed authority

**Priority: high.** `importMap<V>` at `pure/xln.ts:13039-13042` checks only `instanceof Map`, then casts the contents to `ReadonlyMap<string,V>`. `importSections` calls it for `nonces` and `proposals` at `:13109-13110`; `withOgSections` exports that import path at `:13120-13121`. `StoredProposal` requires `votes`, `boardHash`, `action`, and other fields at `:21434`. `foldVote` later obtains a proposal and uses `proposal.votes.has(voter)` at `:21540` onward. A malformed persisted map can therefore enter an `EntityState` with a type the decoder has not proved. This violates the decoder-only authority rule in `docs/fints.md` §3.1.

Compiler counterexample: `/tmp/xln-review-20260928/type-hardening/counterexamples.ts` passes TypeScript 6.0.2 (`bun node_modules/typescript/bin/tsc --strict --exactOptionalPropertyTypes --noEmit --skipLibCheck --target esnext --module esnext --moduleResolution bundler --allowImportingTsExtensions ...`, exit 0). It passes `{ proposals: new Map([['id', 'oops']]) }` to `withOgSections`; the success branch is statically allowed to access `proposal?.votes.has(...)`. Runtime repro `/tmp/xln-review-20260928/type-hardening/repro.ts` exited 0 and printed `{"accepted":true,"proposalType":"string","hasVotes":"undefined"}`. I did not execute the later vote path, so the exact failure disposition there is inferred from the code, not measured.

Smallest compatible fix: replace the generic `importMap<V>` use with field-specific validation for nonce keys/values and complete proposal records, including nested votes. Keep the existing `Map` representation, insertion order, and encoded bytes for valid inputs. Add one malformed persisted-proposal regression and one valid byte/root parity test. This changes malformed-input acceptance, which FinTS already requires, but should be checked against any intentional historical representation before implementation.

## Confirmed limitation: `readonly` collections do not seal committed state

`AccountState.deltas` is a `ReadonlyMap` at `:4680`; `EntityState.accounts` is a `ReadonlyMap` at `:11430`; `Runtime.entities` is a `ReadonlyMap` at `:29411`. TypeScript accepts an aliased mutable `Map` in each slot. The compiler fixture above assigns mutable maps to AccountState and EntityState and passes. A runtime repro at `/tmp/xln-review-20260928/type-hardening/alias.ts` formed an AccountState with a mutable alias, hashed it, mutated that alias, and hashed the *same state object* again: `rootChanged:true`, from `ba21caa7...e0024ad` to `f49267bf...d55993d`. This proves the type does not establish immutable committed values. It does **not** prove a canonical production constructor currently leaks such an alias; local helpers such as `mapSet` copy maps. Treat this as an ownership/decoder audit target, not an assertion of observed production divergence. A narrow fix is to copy externally supplied maps at admission and ensure no mutable alias escapes, with a test at the actual boundary. `Object.freeze` on a Map alone would not establish this guarantee.

## Brand authority gap, with downstream validation

`Hash` is minted by a 64-lowercase-hex validator at `:539-540`, but two `j_event_claim` producers cast an optional block hash or `""` to `Hash` at `:2188` and `:33892`. This permits an empty string at a site typed as validated Hash. `claimParts` later calls `claimBlock` at `:6003`, and `claimFailure` reports invalid block hash at `:8295`; thus I found downstream validation, and I do not claim an invalid claim is certified. The issue is premature static authority: code between production and validation can assume a guarantee it does not have. If blank is a legal transitional sentinel for parity, model it explicitly as `Hash | ""` until the claim boundary; if not, validate before construction. Preserve existing rejection behavior and bytes for valid claims.
