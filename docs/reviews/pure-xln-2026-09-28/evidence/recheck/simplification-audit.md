# Independent read-only recheck: simplification lenses

Revision `0d3a097b782b65b08358299fa0419e65498edc57`; source `pure/xln.ts` has 47,878 lines. This checks `ponytail-audit.md`, `overbuild.md`, `code-simplifier.md`, `creative.md`, `simplify.md`, and the corresponding synthesis in `report.md`. No source edits, expensive tests, or benchmarks. Exact-symbol repository searches excluded generated bundles; absence of references is repository evidence, not a guarantee about external/dynamic imports. Structural search used `ast-grep --lang ts` for Map filter shape. Verdicts distinguish observed code from proposed behavior.

## Decisive correction

**Reject the proposed generic `mapDelete` replacement as behavior preserving.** `pure/xln.ts:258-259` removes entries using `key !== k` (Strict Equality), whereas `Map.delete(k)` uses SameValueZero. For `k = NaN`, current `mapDelete(new Map([[NaN,"x"],[1,"y"]]), NaN)` retains both entries; `new Map(m).delete(NaN)` removes the first. A Bun one-line reproduction returned old size 2, native size 1. The generic signature `K` permits `number` and `NaN`; several real calls use numeric keys (`xln.ts:2019-2020,2545,5730,6047`). No legal protocol path producing a NaN key was established, so this disproves the *generic equivalence claim*, not a demonstrated live financial divergence. A conditional `Number.isNaN` compatibility branch or an explicit non-NaN key invariant would be needed before the change. `mapSet` (`:252-253`) can be implemented with `new Map(m); set(k,v)` under native Map semantics, but that adds a style-gate violation and is not a measured saving. The original `new Map([...m,[k,v]])` already keeps replacement position.

## Code-simplifier claims

1. **`foldResult` (`:42-47`): confirmed contract mismatch.** `[...xs]` fully advances a generic iterable before any reducer callback; the first error suppresses later callbacks only. A lazy `for...of` repairs iterator visitation and removes a full array materialization, but changes generator side effects/`return()` timing and violates current `no-loop`/`no-let` style gates. It is not behavior-preserving for arbitrary `Iterable`. `mapAccumResult`, `traverse`, and `strictFold` inherit iterator timing, but `everyResult`/`someResult` still iterate after a boolean answer even with a lazy `foldResult`: their callback returns successful `ok(false/true)`, not refusal. The main report states this correction; “direct beneficiary” in `code-simplifier.md` is too broad.
2. **`stampClaim` early-return sketch (`:9531-9544`): semantically credible, type shape credible, not compiled.** It calls `claimRowOf`, `claimWitnesses`, `claimStep`, then `claimEvidence` in original order and maps to `stampedClaim`; inferred `Result<StampAcc,ClaimError>` fits those local signatures. Replacing the nested chains with an eagerly constructed `all({...})` would change evaluation order and is rightly rejected. Named local results may be longer in physical lines; readability is opinion. The same pattern for `checkAccountHanko` and `planCrossFill` was suggested only, not proven equivalent.
3. **`mapModify` four sites (`:8856,26437,39617,40459`): pattern exists.** Each calls `mapSet` after reading that same key, with current-value dependency. `mapModify(m,k,f)=mapSet(m,k,f(m.get(k)))` preserves fresh Map and insertion position for ordinary values, invokes callback once, and adds no deletion. It does not reduce copies. A key/getter with side effects could observe a changed count of property evaluation at rewritten call sites; canonical records are ordinary data, but absolute observational equivalence of arbitrary JS objects was not proved. Whether it improves readability is opinion; helper itself adds surface and may not save lines.
4. **`T`/`L` ABI cursor rename (`:466-491`): valid readability suggestion, no semantic effect if identifier-only.** The section has six constructor calls: four `T` and two `L`. They are local constructors with brand casts. Renaming to `asAbiTuple`/`asAbiLength` exposes those casts at call sites. No need to touch the unrelated generic type parameter named `T` later in the file.
5. **Rejecting generic pipe/reducer/orderbook fold/global `at` rename:** design judgments with sensible trust-boundary rationale; no measured savings or correctness proof. The two orderbook paths have visibly different logic. “Use exact replay for every change” is a release verification recommendation, not evidence the proposals are already compatible.

## Simplify claims

1. **Refresh-marker shape (`:9783-9790,16910-16931`): type hole confirmed, closed union requires boundary work.** Current type permits `reason:"issued"` without height/hash and permits issued fields on other reasons. The in-file producer of issued markers (`:17037`) supplies both; unissued producer (`:17055`) does not. `needsBoardRefresh` uses `?? ""`. However the old canonical persisted type at `core/types/account.ts:312-318` also declares both issued fields optional, the old constructor accepts independent `reason` and `issued` (`core/entity/tx/state-effects/board-rotation-hanko-refresh.ts:129-145`), and storage carries this field (`core/storage/schema/account-field-tags.ts:29`). The 150-case parity test constructs legal examples but does not prove all historical records conform. A closed union can be a compile-time view for validated records; it cannot safely retype arbitrary persisted records with a cast or remove fallback until decoding/migration policy is set. Two constructors likely add code, not simplification in lines.
2. **Hash-to-`canon` fallbacks (`:29613,29696-29714`): observed, severity/reachability unproven.** `frameIdOf` replaces a `hashEntityFrame` error with canonical text during proposal-conflict comparison; `jPrefixKey` and `laneKey` replace failed hash with canonical text in merge keys. `mergeEntityInputs` already returns `Result` (`:29943`), and `mergeKey` is Result-typed, so an error route exists. But `frameIdOf` and `laneKey` return string today; threading failure changes APIs and possibly reject priority. The exact error types must be mapped to `RuntimeError`, preserving valid keys and ordering. No malformed-input vector or old-code comparison proves an externally visible divergent outcome; this is a real silent-fallback code shape and scoped investigation, not a verified exploit or a safe refactor yet.
3. **`frameTxMessages` failure erasure (`:7779-7790`): confirmed code shape, proposed `Result` threading requires transaction analysis.** It is called once, by `acceptReceived` at `:10513`, after `install` creates an `OpenAccount`; errors become `[]`. The nested `map(settled, ...)` currently cannot represent `BodyError` from this replay without changing return plumbing. `candidate.draft` already contains a folded state; a valid candidate may make replay failure unreachable, but no proof/repro was supplied. Calling it a confirmed dropped-output defect is too strong. A regression must force a failure after an otherwise admitted candidate and compare the old code's disposition before changing consensus behavior.
4. **Rejected alternatives:** `Lane` slots and Account replica phases visibly serve distinct legal states; no exclusive union is justified. `SubmitJournal`'s duplicate-looking fields are used by `journalFingerprint`; deletion requires recovery proof. `HostChange.changed` is consumed at the cited progress decision and is not safely derivable from object identity. These are supported reasons to retain information; all claims of “best” readability remain judgments.

## Main-report higher-order synthesis

- Existing `opt`/`fields`/`decodeFields` are real vocabulary, but F2's field decoder sketch (`report.md`) explicitly remains uncompiled. `mapModify` is optional and supported only as a readability helper; it is not a performance fix.
- The `withProgress` `mapSetAll` sketch is equivalent for its current `lastConsensusProgressAt` update values even with duplicate progressed keys, because each entry preserves fields from the original `local` and writes the same `at`. It cannot generalize to folds where a later value depends on a previous write. `withPrunedHistory` and `withWitnesses` are such sequential surfaces.
- The report properly downgrades alternate hash identity and `frameTxMessages` to unproven external divergences and refresh-marker closure to a persisted-data question. It also correctly avoids adding the two deletion estimates.
- The summary's claim that the “clearest static candidates” can be removed is bounded to current repo consumers. In particular, adapter removal changes an exported fixture API if any hidden caller exists. The claimed line savings and performance effects should not be reported as achieved.

## Independent bottom line

**One proposed simplification is falsified outright:** generic native `Map.delete` replacement changes `NaN` behavior. **Two more require explicit contracts:** `foldResult` lazy loop changes arbitrary iterable behavior and fails the existing style gate; refresh-marker closure requires a persisted-record validator or migration. The dead-export cuts are plausible static cleanups, but their exact line savings, public surface impact, and final transaction-kind completeness remain unverified. The hash/message error paths warrant narrow regressions before changing production behavior. No performance claim was established by this review.
