# xlnc: четыре сети и ограниченный запуск

Дата: 2026-09-05. Исследованный SHA: `b97c454d605e750a08da7ff6baab645330175468`.
Статус: предложение, без изменения консенсуса, конфигурации сетей или лимитов капитала.
Владелец выбрал Ethereum, TRON, Base и экспериментальную XLNC; H1–H3 и MM сначала наши.
Начальный капитал: $1 000 суммарно. Название: **«ограниченный mainnet / soft mainnet»**.
Это обозначение масштаба риска, а не доказательство готовности или защищённости.

## Решение

- XLNC должна выполнять роль J: регистрация/полномочия Entity, резервы, залог, settlement, disputes и нужные доказательства.
- Платежи, маршрутизация, credit и swaps остаются в R/E/A. Не записывать каждый платёж в глобальную цепь.
- Полная локальная проверка XLNC — полезная цель. Она не означает локальную полную проверку Ethereum, TRON и Base.
- Повторно использовать зрелый механизм консенсуса и исполнение контрактов; новую consensus-механику сейчас не создавать.
- Настоящая «только XLN» — правило проверки блока всеми узлами. Ограничение RPC или честность нашего валидатора этого не обеспечивают.

## Что уже существует

| Граница     | Наблюдение в коде                                                                                                  | Следствие                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| J → Entity  | [Каноническая архитектура](core/rjea-architecture.md), [J machine](runtime/jurisdiction.md)                        | Внешний RPC не становится authority редьюсера; наблюдения проходят canonical validation     |
| Адаптер     | [JAdapter](../core/jurisdiction/adapter/types.ts): `rpc`, `tron`, `anvil`, `browservm`                             | XLNC не требует нового Account/Entity финансового пути                                      |
| Финальность | [rpc-finality.ts](../core/jurisdiction/adapter/rpc/rpc-finality.ts): Ethereum 12 блоков, прочие EVM 2 по умолчанию | Эти числа не доказывают consensus finality; Base/XLNC нельзя подключать с неявным default   |
| Dev-сети    | [chain-ids.ts](../core/jurisdiction/adapter/chain-ids.ts): 31337/31338 включают dev-поведение                      | XLNC получает отдельные chain ID, genesis hash и release manifest; не переименованный Anvil |
| Капитал     | [Текущая policy](../ops/capped-testnet-policy.json): `riskCapUsd: null`, enforcement отсутствует                   | $1 000 пока решение владельца, не программно обеспеченный предел                            |

В проверенных production-файлах нет runnable XLNC validator/fullnode. Старые типы `Xlnomy` с именами EVM-движков не доказывают реализацию сети.

## Минимальный путь: специализация без нового финансового движка

| Вариант                                                            | Что получаем                                                          | Ограничение                                                             |
| ------------------------------------------------------------------ | --------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Готовый EVM-клиент + наши контракты + operator policy              | Быстрый экспериментальный стенд с существующим JAdapter               | Цепь технически general-purpose; не удовлетворяет строгой XLN-only цели |
| Готовое consensus/execution ядро + проверяемый всеми XLN admission | Желаемая специализированная J-сеть; контрактная семантика сохраняется | Нужны доказанный validation hook/минимальный fork и протокольный выбор  |
| Новый native J interpreter + новый consensus                       | Максимальная свобода                                                  | Два новых критических компонента; отдаляет mainnet и MML                |

Рекомендация: второй вариант как целевая спецификация; первый только как явно обозначенный стенд, если он ускоряет проверку.
Нельзя незаметно выпустить первый вариант под обещание второго. Реализацию целевой сети начать после выбора validation boundary.
В XLN admission нужно охватить весь execution graph: прямые вызовы, внутренние calls, создание контрактов, upgrade и входящие native transfers.
Одного allowlist `to`/selector недостаточно, если разрешённый контракт может создавать/вызывать произвольный код.
Разрешённые bytecode hashes, операции и upgrade-путь должны проверяться полным узлом; выпуск нового набора — явное изменение протокола.

Besu/QBFT — конкретный кандидат для стенда: существующий PoA и управление составом валидаторов. Для Byzantine fault tolerance Besu требует минимум четыре валидатора. Это ещё не выбор движка XLNC. [QBFT](https://docs.besu-eth.org/private-networks/how-to/configure/consensus/qbft)
Для массового desktop bundle у Besu существенный минус: документация частных сетей указывает минимум JVM около 4 GB в зависимости от окружения. Измерить реальный бюджет до выбора; маленькая J-нагрузка не доказывает маленький клиент. [Требования Besu](https://docs.besu-eth.org/private-networks/get-started/system-requirements)

## Полная нода у пользователя

```text
UI → локальный xln Runtime → JAdapter → локальный XLNC verifier → XLNC peers
                                      ↑
                   отдельный node process; без validator/private-wallet keys
```

- Desktop installer предлагает и включает verifier по умолчанию с явным показом диска/памяти. Пользователь может остановить его; UI показывает потерю режима локальной проверки.
- Валидатор — отдельная роль с отдельным ключом. Тысяча fullnodes не превращает один validator в тысячу независимых producers.
- Сначала полная проверка от опубликованного genesis; допустимо удалять старые промежуточные состояния после проверки. Fullnode и archive — разные обязанности. [Полная проверка](https://ethereum.org/developers/docs/nodes-and-clients/)
- Snapshot ускоряет загрузку только при явно заданной проверке его root/истории. Snapshot от нас без независимой верификации — доверенный bootstrap, не «всё проверено от genesis».
- Браузерная страница не устанавливает desktop daemon сама. BrowserVM не является сетевым XLNC fullnode; для browser-only клиента нужен отдельно доказанный verifier/связь с локальным companion. Хранилище браузера имеет квоты и режимы persistence. [Storage Standard](https://storage.spec.whatwg.org/)

Показывать отдельно: `локальная проверка`, `проверен до блока`, `источник bootstrap`, `отставание`, `независимые операторы`.
Если узел отстал, не переключать финансовую authority на удалённый RPC молча. Recovery/синхронизация доступны; новые операции ждут нужную готовность J.

## Что защищает localhost

| Угроза                                                | Эффект локальной полной проверки                                                                      |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| RPC выдаёт неверный balance/log/state                 | Узел отвергает недопустимую историю при корректном клиенте и доверенном genesis                       |
| Единственный validator цензурирует settlement/dispute | Не решает: корректный блок может не содержать нашу транзакцию                                         |
| Validator подписывает две допустимые истории          | Можно обнаружить при получении обеих; нельзя одной локальной проверкой выбрать общий порядок для всех |
| Узел изолирован от честных peers                      | Правила проверяются, но актуальность/доступность истории не гарантирована                             |
| Вредоносное обновление, compromised host или ключ     | Не решает; bundled monoculture увеличивает общий blast radius                                         |

Проектный минимум: loopback-only bind; OS IPC с правами пользователя, где поддерживается; иначе аутентифицированный loopback endpoint.
Проверять Host/Origin и WebSocket Origin, закрыть wildcard CORS, ограничить методы, размер/частоту запросов; wallet signing и validator/admin API вынести отдельно.
Локальный порт доступен другим локальным процессам. CORS не заменяет authentication. Не хранить разблокированный signing account в доступном RPC. [Geth RPC](https://geth.ethereum.org/docs/interacting-with-geth/rpc), [Besu RPC authentication](https://docs.besu-eth.org/public-networks/how-to/use-besu-api/authenticate)
Регрессионная цель: чужой Origin/Host, неавторизованный WS и административный метод отвергаются; штатный UI читает chain и отправляет только уже подписанную транзакцию.

## Доступность, обновления и децентрализация

- Один validator допустим как раскрытый централизованный эксперимент: его остановка останавливает J, включая выводы/диспуты. Бэкап ключа и восстановление не дают Byzantine safety; нельзя одновременно запустить две копии signing identity.
- На старте держать несколько реплик полных блоков на разных машинах и проверять восстановление из них. Разные машины одной фирмы — availability, не независимая governance.
- Следующий этап: независимые операторы и выбранный quorum, общий genesis/rules, проверенные смена validator set и отказ одной стороны. Для QBFT пример 4 независимых validator с tolerance 1; 4 наших процесса не дают независимости. [QBFT](https://docs.besu-eth.org/private-networks/how-to/configure/consensus/qbft)
- Подписанные releases с фиксированными hashes, воспроизводимая сборка, постепенное обновление и локальная проверка manifest уменьшают риск supply chain. Независимый совместимый verifier позже уменьшит monoculture; второй consensus implementation сейчас не P0.
- Исторические блоки должны быть доступны новому узлу без единственного сервера. Опциональная публикация block hash во внешней сети доказывает существование commitment, но сама не даёт данные, forced inclusion, exit или безопасность rollup.

XLNC хранит J-операции и необходимые доказательства; приватные Account frames и каждый off-chain hop туда не публикуются.
Ограничить стоимость валидации, block bytes/gas и рост состояния. Дешёвый gas требует защиты от заполнения диска; «бесплатно всем без границ» несовместимо с нодой у каждого.
Для аварийного выхода нужны доступная J и inclusion. Не обещать, что локальная копия автоматически выводит деньги при остановившемся единственном validator.

## Четыре сети, одна ограниченная экспозиция

| Сеть              | Перед допуском капитала                                                                        |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| Ethereum          | Проверенные bytecode/address/domain, live J, вывод/диспут, явная политика финальности          |
| TRON              | Реальные TVM/write/receipt/resource пути и solidified head; Anvil не свидетельство             |
| Base              | Контрактные артефакты и отдельно unsafe/safe/finalized наблюдения; два L2-блока не L1-finality |
| XLNC experimental | Genesis/rules/validator manifest, проверка полного узла, реальные активы и их issuer/backing   |

Base связывает finalized L2 head с L1-finality. Для финансового допуска нужно сознательно выбрать уровень риска, не таймер «готово через N секунд». [Base derivation](https://docs.base.org/specifications/base-protocol/consensus/derivation)
Четыре сети дают шесть пар и двенадцать направлений; Ethereum/Base и наши H1–H3/MM не являются независимыми источниками риска.
Первое упражнение — один минимальный реальный round trip на каждой новой границе с выводом; полный cross-J matrix остаётся финальным gate.
В общий $1 000 учитывать ликвидность, gas/resource balances, dispute reserve и уже потраченные deployment fees; лимит активов отдельно от лимита операционных расходов.
Не размазывать капитал равномерно по четырём сетям: измерить deploy/gas и обязательный резерв, остаток дать рабочей ликвидности. Если costs не помещаются — сузить одновременную экспозицию, не скрыто повышать бюджет.
Токен XLNC с названием USDT не становится Tether USDT. Нужны явный эмитент/погашение/обеспечение; bridge и wrapped asset — дополнительный риск, не бесплатная интеграция.
Лимиты должны применяться до допуска обязательства, включая quotes/аренду/credit и crash recovery; один UI-предел недостаточен. Рост капитала только после измеренного round trip, reconciliation и отдельного решения владельца.

## Следующие решения и доказательство

1. Зафиксировать строгую XLN-only block-validation границу и существующее ядро; не выдавать RPC policy за consensus rule.
2. Утвердить экспериментальную single-validator trust model и доступный пользователю exit при остановке; если exit невозможен — прямо так маркировать.
3. Первый XLNC artifact: genesis → 1 producer + 1 verifier → canonical deployment → reserve → Account collateral → payment → settlement → withdrawal → restart → одинаковые roots/logs.
4. До денег: отказ producer, повреждённый блок, несовместимые rules, неверный snapshot, отсутствующие данные и недоступный RPC дают объяснимую остановку. Никакого автоматического reset genesis.
5. Затем четыре реальные J-границы, полный check и ограниченный ввод капитала; XLNC R&D не задерживает устранение текущего production recovery divergence.

MML измерять уникальной завершённой экономической стоимостью за скользящие 12 месяцев: один платёж один раз, один exchange без суммы обеих legs, без наших круговых перегонов и тестов.
Доля мирового GDP — долгосрочная амбиция, не текущая метрика успеха: оборот платежей и добавленная стоимость GDP методологически различаются.
Ближайшие полезные числа: успешные выводы, потери/расхождения, стоимость завершённой операции, связанный капитал, время recovery и доля действительно локально проверяющих клиентов.
